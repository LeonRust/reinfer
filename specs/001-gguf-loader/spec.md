# Spec: GGUF loader and typed core layer

> Status: proposal · Owner: maintainers · Created: 2026-08-25 · Parent: specs/000-project-mvp

## Problem Statement

P0 requires reading GGUF files with zero Python/torch involvement (constitution §1.3): memory-mapped metadata in milliseconds, typed tensor handles, and a numerically verified Q8_0 dequantization reference — the foundation every later kernel and backend builds on.

## Success Metrics

- Loading a 7B-class model: metadata parse < 100 ms after mmap; full catalog listing no later than 2 s (no touch of weight pages)
- Tensor names/shapes/quant types parse identically to llama.cpp `llama-model-loader` for the same file (golden files produced by `convert_hf_to_gguf.py`)
- Q8_0 dequantization (naive Rust reference) matches a precomputed reference result element-wise within 1 ULP on golden blocks
- RSS increment from metadata mapping ≤ 64 MB (excluding demand-paged weight pages)

## User Stories

1. As a CLI user, I can read `reinfer info model.gguf` and see architecture, dims and quant table within 1 s.
2. As a kernel author, I can get a typed tensor handle (`TensorId`, not string parsing) and decode blocks without touching GGUF internals.

## Acceptance Criteria

- [ ] `GgufReader::open(&Path)` exposes lazy mmap views; standard metadata keys map to a typed enum (`GgufMetadata`)
- [ ] Quant kind enum covers Q8_0, Q4_0, F16, F32 with a full per-kind `dequantize_to_f32` reference function (naive)
- [ ] `TensorId` is a `u32` handle; `tensor(name) -> Option<TensorId>`; `load_bytes(TensorId) -> Option<&[u8]>`
- [ ] Error paths: bad magic, truncation, oversized/overlapping offsets → readable `GgufError` variants, no panic
- [ ] Tests: golden-file unit tests (weights < 100 MB, generated by llama.cpp conversion, cached in CI) + proptest roundtrip on random bytes

## Non-Goals

- No offline weight conversion (delegated to llama.cpp tooling); no GGUF writing; no CUDA-side dequantization (P1)
- No generic dynamic import of unknown quant kinds (unknown → explicit error with byte offset)

## Constraints

- GGUF layout compatible with llama.cpp current format, including `alignment = 32` rules for header/metadata/tensor alignment
- crates/gguf stays `#![forbid(unsafe_code)]` — use memmap2 + byteorder/bytemuck only
- crates/core has no dependency on crates/gguf (DAG, see docs/项目结构.md §2)
